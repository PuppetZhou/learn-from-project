# 维护与扩展

## 一个 skill 的契约

每个 skill 定义自己的触发条件、主要交付、范围、必要输入和完成检查。`description` 写清实际用途，正文从目标与按需导航进入具体工作；无需为了格式一致重写所有有效内容。

约定目录与 YAML 名称相同，使用小写短横线命名。为本 kit 的每个 skill 提供 `agents/openai.yaml` 的显示名称和简短介绍。`references/`、`assets/`、`scripts/` 均按需，不预建空目录。入口无需强制统一字数，但避免把只适用于一个场景的长指南常驻加载。

共享原则只有在多处确实需要时才提炼。运行期不跨 skill 读取相对路径，不将仓库根目录的 AGENTS.md 当作 skill 使用条件。必要的少量通用约束可各自保留，避免为了消除几句话的重复而增加依赖。

## 两个 skill 如何协作

| 请求 | 主导 skill | 交付与边界 |
| --- | --- | --- |
| 解释知识、公式或代码 | learn-from-project | 解释、例子或练习；不自动创建笔记 |
| 整理、补充或关联已有笔记 | obsidian-knowledge-curator | 修改指定笔记；不默认展开授课或测验 |
| 学习后沉淀到知识库 | 两阶段组合 | 教学阶段提供已讲清的主线、例子、来源、未决问题；笔记阶段按保存授权整理，避免照抄聊天 |

这是一种任务分工，不要求启动多个代理。简单任务直接完成，需要组合时才读取另一个 skill。未来“读论文”“实验记录”等新 skill 依照其实际交付增加，不预先创建占位 skill。

## 新增与更新流程

1. 明确真实请求、主要交付和容易误触发的相邻任务，决定新增 skill 还是补充已有参考。
2. 在 `skills/<name>/` 放入 `SKILL.md`、界面元数据与必要资源；链接引用在该目录内闭合。
3. 更新 README 的 skill 索引；外部导入记录来源 URL、提交和改动。尊重上游许可，不把参考链接当作授权声明。
4. 运行结构检查，按变更运行小范围行为检查；检查后使用 `manage.py install <name>` 安装。
5. 用 Git diff 审阅，按完整的行为变更提交。暂以 Git 提交作为版本依据；出现独立发布需求后再引入每个 skill 的版本号。

## 最小行为验收

- 教学：要求解释陌生代码，能追踪实际输入输出并讲清理由；要求直接修复问题，不强制转成课程；纯概念请求不强制写代码。
- 笔记：只要求格式时保护事实、公式与代码；内容精简后仍有必要承接句；默认标题为 `## 1.` / `### 1.1`，不新增更深标题。
- 组合：用户只要求学习时不写 vault；用户要求保存时保留有依据的知识和来源，不把未验证推断转写成事实。

可在临时目录用小样本复核。现有教学 skill 的详细案例位于其 `references/examples-and-checks.md`；笔记格式与保护检查使用其自身脚本。结构检查验证命名、元数据和本地 Markdown 文件链接，不检查外链可用性、锚点、实际渲染或教学效果。
