# 阅读代码与局部知识点

使用提示：本文件提供可选讲解思路，按目标、已有知识和当前反馈取舍。步骤顺序、练习及输出形式可以改变；事实准确与项目授权边界仍需遵守。

## 先区分两种请求

“这套项目怎么运作”可参考 [仓库拆解](repository-walkthrough.md)；本文件聚焦函数、代码片段及知识点。“这个列表推导式是什么意思”需要局部解释。不要把后者扩展成项目入门，也不要用逐行语法翻译回答前者。

## 读函数或代码片段

1. 实际读取入口、相关函数、调用者和必要样例。先用两三句话说清职责与最终结果，不扫描整个仓库。
2. 解释关键输入输出、数据粒度和约束；未知格式先补背景。
3. 将代码分为有意义的处理块，例如解析、筛选、关联、写出。指出哪块体现科学规则，哪块负责运行保障。
4. 追踪一条合成或已核对的真实输入，展示重要变量如何变化、进入哪个分支、结果给谁用。
5. 对关键块解释为什么这样写，比较一个必要的替代方案，指出条件与局限。代码过密时先展开成等价普通写法，明确这是阅读辅助而非生产修改。

引用真实路径和核对过的行号。现有缺陷或与规则不一致之处应明确，不为了讲顺而合理化错误实现。

## 学一个代码知识点

采用“它解决什么问题 → 最小例子 → 执行过程 → 何时用/不用 → 当前代码中的对应”即可。没有项目上下文时用通用小例子，不强行套入 VEP。

例：解释集合时先展示 `["v1", "v1", "v2"]` 与 `{"v1", "v2"}` 的区别，再讨论去重会丢掉重复性和顺序信息。最后连接“唯一 SNV”和“来源条目不能随意去重”的不同用途。

解释字典查找时指出重复键覆盖的风险；解释生成器时展示逐项产生与一次性列表的差别；解释上下文管理器时说明资源生命周期。不默认学习者知道这些术语。

## 连接专业概念与执行过程

重点代码所体现的概念应给出规范名称及通行英文，帮助学习者继续读文档与讨论设计。例如列表推导式（list comprehension）、迭代器（iterator）、生成器（generator）、上下文管理器（context manager）、时间复杂度（time complexity）。这些是示例，不是每次必讲清单。

讲解可以从具体执行进入概念：`yield` 每次产生一个值，执行会暂停，下次迭代再恢复；据此解释生成器、惰性求值（lazy evaluation）及其与一次构造列表的差别。不要只把它称作“省内存的写法”，也不要只报英文名。当前任务涉及性能判断时，再说明内存使用、重复遍历和计算成本的取舍。

把语法、机制和设计理由连接起来；涉及复杂度等定量关系时解释公式中的规模变量与成立条件。不需要把所有相关术语一次讲完，已讲清的名称后续自然使用即可。

## 重要内容的选择

优先解释改变结果含义的分支、关联键、索引/维度、循环边界、状态和返回值。imports、格式化、日志、类型标注通常简述；如果当前问题正是环境、日志或类型，则提升为重点。

不能把“辅助代码”一律略过：例如文件写入结束时的行为，可能决定是否留下被误认作成功的半成品。

## 引导问题

预测一个中间值；改变输入后哪个分支会执行；如果删除这一句有什么具体后果；这一函数为什么返回这个结构。按当前障碍选择，不把每一行都变成问答。

讲完后让学习者说明关键路径或修改点。解释代码的请求不授权实际重构；改进建议应与已执行修改分开。
