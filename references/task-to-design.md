# 从目标逐层拆解到代码设计

使用提示：本文件提供可选讲解思路，按目标、已有知识和当前反馈取舍。步骤顺序、练习及输出形式可以改变；事实准确与项目授权边界仍需遵守。

## 核心职责

帮助不知道如何下手的人看到：目标怎样变成步骤，步骤怎样变成函数/模块，各部分如何协作，以及何时值得优化。现有代码只是需要审查的实现，不是唯一正确设计。

## 第一步：把需求说具体

从一句话任务中提取：输入是什么、输出是什么、一行/一个对象代表什么、哪些科学含义必须保持、怎样判断完成。数据处理任务通常可用一组小输入和预期输出澄清需求。对象或格式不清楚时，切到背景场景补足再返回。

示例：“整理变异”太宽。可收敛为“读取来源条目，逐条判断资格，保留合格条目，并生成由它们支持的唯一 SNV 索引”。资格定义来自现行规则，不由教学擅自决定。

## 第二步：先写人话步骤

不从类、框架或文件名出发。让学习者看到最小流程：读取 → 解析 → 判断 → 转换/关联 → 输出 → 核对。并非每个任务都需要全部步骤。

每一步回答：为什么存在、输入是什么、输出是什么、下一步依赖什么、失败怎样表示。明确处理顺序的理由，而不只是画箭头。

例如先筛条目再汇总 SNV，是为了让索引的资格来自实际保留条目；先获得 SNV 集合再回查全部条目，可能传播资格。用两条共享 SNV 但资格不同的合成记录说明。

## 第三步：选择最简单的表示与边界

| 选择 | 有助于理解选择的问题 |
| --- | --- |
| 列表、集合、字典或表 | 需保留顺序/重复吗？按什么查找？键能否一对多？ |
| 一个函数 | 是否有清晰输入输出、独立判断、可复用逻辑或值得单独验证的规则？ |
| 分开读取与计算 | 是否需要用合成数据核验核心规则，而不依赖大文件或外部工具？ |
| 模块/阶段拆分 | 是否存在不同职责、昂贵步骤、独立依赖或有价值的恢复边界？ |
| 配置与代码分开 | 哪些路径、版本或运行资源会变化，哪些是处理逻辑？ |
| 显式状态 | 是否需区分未知、排除、失败和未评估？布尔值够不够？ |

不要把每个步骤机械拆成一个文件。简单脚本可先采用几个函数；只有明确需要时再引入类、调度器或插件体系。

## 第四步：把设计映射到实现

先给函数签名或简短伪代码，说明调用关系。再展示一条记录如何经过函数、得到哪些中间值和最终结果。已有项目中链接实际入口与关键实现，区分“当前实现”“当前规则”和“建议设计”。

可以用一张小表：需求 → 负责函数 → 输入/输出 → 下游依赖。不要用目录树替代架构解释；用户能看到文件夹并不意味着知道各模块为何存在。

## 第五步：先验证，再扩展

先检查最小例子、一个边界和一个能区分错误实现的反例。然后逐步扩展为文件、批次、多来源。扩展前说明新增加的困难，以及为什么原设计需要变化。

只讨论与当前代码有关的优化：重复扫描、重复计算、内存占用、昂贵 I/O、失效范围、可读性。说明收益、代价和适用条件。未经测量的性能建议标为假设，不报虚构提速。

## 引导与完成标准

让学习者尝试回答一个设计问题：新增字段放哪里？某条规则变了哪些步骤需重算？为什么使用集合而不是列表？删除一条来源后共享请求还能保留吗？

完成标准是能复述目标到步骤的逻辑，并独立作出一个小设计选择；不是记住当前项目的所有函数名。
