# 原创输出样本：为什么把脚本拆成几个部分

用途：仓库导览和从目标设计。下列文件名是虚构示范，不能用作真实项目路径或设计意图的证据。

任务：从一个 TSV 读取记录，按已确认规则筛选，输出合格记录及唯一 ID。

| 部分 | 职责 | 输入 → 输出 |
| --- | --- | --- |
| `main.py` | 接收参数、组织调用 | 文件路径 → 流程执行 |
| `io.py` | 读写格式 | TSV 文本 ↔ 记录 |
| `rules.py` | 判断资格 | 一条记录 → 判断/原因 |
| `build.py` | 组合结果 | 合格记录 → 表与索引 |

> 先看一次运行，而不是背四个文件名。入口取得路径，读取层产生记录，规则层判断资格，构建层组织输出。我们把规则与文件读取分开，是为了用几条内存中的合成记录检查规则，不必每次打开大文件。
>
> 这不意味着四个步骤必须放进四个文件。项目很小时，在一个脚本中定义几个清晰函数就足够。只有职责、复用或维护需求使分离有实际价值时，才增加模块。
>
> 如果只是输入路径变化，通常调整参数即可；如果 TSV 改成带嵌套信息的格式，读取/解析层要重新审查；如果收录条件改变，规则及其下游结果需要复核。模块的联系要从输入输出与依赖判断。

设计练习：新增“排除原因汇总”应在哪些地方传递信息？先判断现有规则返回值是否足够，再考虑新增文件。

优化讨论：若同一文件重复扫描，先测量读取成本，再考虑合并扫描；同时解释这样做是否让模块过度耦合。不能只因“少读一次”就保证更快或更好。
